# Воронка и избранные кандидаты HR

Реализация P1 из [плана функций](REFERENCE_FEATURE_PLAN.md), 8 октября 2026. Код написан самостоятельно по продуктовым идеям примера. Основной сценарий обратного найма, правила assessment и формула matching сохранены.

## Где показать

1. Войти как `employer@demo.test` / `DemoPass123!`.
2. «Найти специалиста»: выбрать потребность, нажать «Показать подборку». Блок «От подбора до встречи» показывает активность выбранной версии роли. Кнопки переключают реальные и тестовые данные; в демо используется тестовый срез.
3. На карточке нажать «Сохранить кандидата». Открыть «Избранные кандидаты»: карточка сохранится после перезагрузки. Повторная кнопка убирает её из списка.
4. Изменить условия роли: текущая версия получает отдельный список и отдельную воронку. Прежние данные доступны через выбор версии. Приглашение из исторического списка заблокировано; удаление сохранения доступно.
5. Кандидат снимает публикацию или меняет обязательные условия: при обновлении избранного карточка скрывается. Показывается только число недоступных сохранений, без идентификаторов или причин, раскрывающих приватные предпочтения.

Три ранее добавленные тестовые встречи сохранены при обновлении Compose. Воронка этой роли показывает 3 приглашённых, 3 принявших и 3 с назначенными встречами. Прошедшее время календарной встречи само по себе не означает проведённое интервью: последний этап требует подтверждений обоих участников.

## API и данные

Все маршруты требуют работодателя и принадлежности потребности ему. Чужая потребность или версия другой потребности возвращает 404. Контракт типизирован в [OpenAPI](openapi.json).

| Маршрут | Поведение |
|---|---|
| `GET /api/v1/employer/needs/{need_id}/funnel?role_version_id=…` | Активность точной immutable-версии; без параметра — текущая. Версии и отдельные `real` / `synthetic` счётчики |
| `GET /api/v1/employer/needs/{need_id}/shortlist?role_version_id=…` | Только приватный список владельца и доступные публичные карточки; актуальные версии состояния, `unavailable_count` |
| `PUT /api/v1/employer/needs/{need_id}/shortlist/{candidate_id}` | CSRF; тело `{role_version_id, expected_version, saved}`. Начальная ожидаемая версия 0; первое сохранение возвращает 1 |

Стадии воронки считают уникальных кандидатов: `matched` — присутствовавшие в сохранённых подборках; `invited` — получившие приглашение; `accepted` — действующее принятое приглашение; `scheduled` — назначенная, не отменённая встреча по принятому приглашению; `held` — оба участника подтвердили интервью. Повторы не увеличивают числа. Отозванное приглашение остаётся в «Приглашены», но не входит в «Приняли». Приглашения из банка могут отсутствовать в подборках, поэтому стадии не обязаны монотонно уменьшаться. Проценты конверсии и оценка качества matching здесь не вычисляются.

Synthetic определяется существующим `product_event_data_mode`: demo/test или синтетическое происхождение любого участника. Воронка не отдаёт идентификаторы кандидатов, контакты или их решения save/hide в ленте. Состояния приглашений — агрегат активности работодателя, не отчёт о релевантности.

Таблица `employer_shortlist`: владелец, потребность, точная версия роли, кандидат, `saved`, `state_version`, `updated_at`. Уникальность `(employer_id, role_version_id, candidate_id)`; версия состояния положительна. Миграция `b26c19d745ef` после `f7c2a1d93e10` создаёт только эту таблицу. Существующие встречи, роли, аккаунты и попытки не переписываются. Downgrade удаляет таблицу избранного; для обычного обновления он не нужен.

Удаление — `saved=false`, запись сохраняется для CAS. Доступные несохранённые записи возвращаются API, чтобы клиент знал актуальную версию при повторном сохранении; UI отображает только `saved=true`. Параллельная команда с устаревшим `expected_version` получает 409 `SHORTLIST_VERSION_CONFLICT`. UI перечитывает состояние, сообщает о конфликте и не повторяет действие автоматически. Повтор команды с актуальной версией и тем же значением идемпотентен.

## Ограничения и проверки доступа

- При чтении и сохранении используются `eligible` / `can_search` и block guard: публикация, согласие на обработку, 18+, доступность, подтверждённая категория и балл, зарплата/формат/город и стек.
- Новое сохранение требует текущей опубликованной свежей роли. Снятие собственного сохранения разрешено и для исторической роли или недоступного профиля.
- Карточка содержит только поля публичного подбора. Приватные контакты, имя, зарплатный минимум, preferences и причины скрытия не выдаются. Уже существующий endpoint контактов по accepted/grant остаётся отдельным.
- Порядок блокировок в записи соответствует приглашениям: профиль кандидата → потребность → запись избранного. CAS и уникальность проверены настоящими PostgreSQL race tests.
- Перед приглашением сохраняются существующие серверные guards актуальных условий и evidence; shortlist их не обходит.

## Что проверить участнику после pull

1. Применить миграции на своей базе до `b26c19d745ef`. В существующей базе встречи/приглашения/попытки должны сохраниться; не очищать volume и не запускать factory reset ради обновления приложения.
2. HR: сформировать подборку → сохранить профиль → открыть избранное → перезагрузить → удалить → сохранить снова. Контакты не должны появиться в карточке избранного.
3. Две вкладки одного HR: открыть одну роль в обеих, сохранить одного кандидата из первой, повторить из второй. Вторая получает сообщение о конфликте и актуальное состояние; сохранение не должно незаметно отменяться.
4. Кандидат: снять публикацию либо доступность → HR обновляет избранное. Карточка скрывается; возвращение публикации возвращает доступную сохранённую карточку. Проверить также блокировку компании и зарплату/формат без раскрытия причины HR.
5. Создать новую версию условий: текущее избранное пустое, прежнее доступно в выборе версии. Новое приглашение из старого списка недоступно. Текущая и историческая воронки не смешивают активность.
6. Назначить/отменить встречу; подтвердить проведённое интервью сначала кандидатом, потом HR. Последняя стадия растёт только после второго подтверждения. Повторные подборки и подтверждения не увеличивают числа.
7. Войти другой компанией: чужой shortlist/funnel недоступны. Проверить телефонный viewport 390px и клавиатуру; горизонтального overflow быть не должно.
8. Проверить Qwen на своих синтетических формулировках: числовая зарплата, QA/Backend-категория, индивидуальный/командный вклад, неизвестные поля. Модель создаёт только редактируемый черновик; пользователь явно применяет его. Уточнение result_scope включено в этот commit, но не выкатывалось новой пересборкой после просьбы пользователя остановить deploy.

Автоматические команды: `python -m pytest -q`; для PostgreSQL — выделенная `*_test` база через `TEST_DATABASE_URL`; `cd frontend` → `npm run build` → `npm run test:e2e`. Live-AI сценарии отдельно включаются `FSP_SIGNAL_LIVE_AI=1` с настроенным серверным ключом; ключ не передавать во frontend или Git.
