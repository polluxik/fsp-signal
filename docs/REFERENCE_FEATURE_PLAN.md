## Почему это усиливает демонстрацию

Кандидат сразу понимает, что мешает появиться в подборке. После неудачного теста получает полезный план подготовки, а не тупик. HR получает подтверждённую категорию и evidence; кандидат контролирует публикацию и контакты. На защите показываем связный путь: маршрут → тест → отчёт → профиль виден → предложение с условиями → календарь → итоги встречи. Проценты навыков — результат конкретного набора заданий, а не вероятность найма или точная оценка человека.

## Контракт для CODEX: первая реализация

1. Добавить отдельный FastAPI router с типизированными read-only ответами. Без новых таблиц и миграций.
2. `GET /api/v1/candidate/journey`: данные только текущего кандидата; этапы, причины закрытой видимости, активная неистёкшая попытка, необязательный статус ФСП. Для видимости использовать существующий `can_search`, а не новую формулу.
3. `GET /api/v1/candidate/assessment-attempts/{id}/report`: только владелец, только scored; расчёт по сохранённым вопросам/ключу/ответам и существующему grader. Отдавать только агрегаты и упражнения, без ключей, ответов, seed, question IDs и формулировок заданий. Не менять результат, грейд или профиль. Старый отчёт не смешивать с новой подтверждённой категорией.
4. В UI: маршрут на вкладке «Для меня», переходы по этапам; план теста из taxonomy; отчёт после submit и отдельная кнопка в истории. Loading/error/retry; мобильная компоновка; aria progress labels. Незаписанные поля формы не считать завершённым этапом.
5. Проверить отсутствие доступа работодателя/другого кандидата к отчёту, отзыв согласий/доступности, expired resume, failed/perfect/partial structured результаты, отсутствие answer leakage, оба браузерных сценария. Обновить OpenAPI и handoff.
6. Сначала пройти SQLite/build/Playwright, затем PostgreSQL races в отдельной `*_test`, когда Docker отвечает. Не отмечать PG проверку выполненной по чужому отчёту.

## Передача следующих этапов

P1 выполнять небольшими изменениями: (1) воронка из действующей invitation state machine; (2) shortlist с CAS/guard и тестами доступа; (3) фильтры внутри snapshot; (4) CI и публикация стенда. P2 не включать в основной pitch до измерений. Не подменять свои данные/валидацию чужими synthetic метриками. Текущая .env остаётся игнорируемой; чужие конфиги/учётные записи/ключи не импортировать.

## Что реализовано в этой итерации

Первый этап завершён: `backend/candidate_progress.py` с типизированными `/candidate/journey` и `/candidate/assessment-attempts/{id}/report`; frontend `features/progress/` с маршрутом, планом теста и разбором. Отчёт открывается сразу после submit и из истории. Активную попытку можно продолжить с маршрута после перезагрузки. Формы, данные assessment, формула matching и ограничения попыток сохранены; новые маршруты ничего не записывают. Приватный отчёт показывает агрегаты и упражнения без решений заданий. План работает без LLM/GPU.

Проверка 8 октября на текущем Windows: **185 backend passed на PostgreSQL**, **175 passed / 10 PG-only skipped на SQLite**, production TypeScript/Vite build. Все 20 существующих браузерных сценариев и 2 новых прошли; 3 opt-in live-AI пропущены. Первый полный браузерный прогон дал 21 passed и ошибку сравнения `innerText`/`textContent` в новом тесте; после исправления проверки обе новые проверки прошли отдельно. Отчёт на мобильном 390px визуально проверен, горизонтального overflow нет.

Docker восстановлен обходом runtime socket; Compose `fsp-signal-smoke-20261007` работает на `http://127.0.0.1:58080`, Mailpit на `http://127.0.0.1:8025`. Проверены readiness, совпадение live/export OpenAPI, вход демо-кандидата, read-only journey, создание нового аккаунта, доставка письма worker → Mailpit, корректный адрес ссылки, подтверждение и вход. **Регистрация существовала до этой итерации**; здесь проверен полный контейнерный email-путь. Внешний SMTP и публичный деплой не проверены.

P1/P2 в таблице остаются планом. Shortlist HR, новая воронка, расширение банка/IRT и CI ещё не реализованы этой итерацией.
