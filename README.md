# ФСП Сигнал — рабочий прототип

Веб-прототип обратного найма по [спецификации](docs/PRODUCT_SPEC.md). Компания ищет кандидата по категории, присвоенной тестом, и первой направляет приглашение с зарплатой. Контакты открываются только компании, приглашение которой кандидат принял.

Работодатель может возвращаться к сохранённым подборкам после обновления страницы и уточнять поиск от предыдущей подборки. Если кандидат снимет профиль с публикации, в старом результате его карточка больше не показывается.

Кандидат может заполнить профиль вручную или загрузить PDF-резюме с текстовым слоем. Импорт показывает черновик полей; исходный PDF не сохраняется, профиль не публикуется до отдельного сохранения и согласия. Скан без текстового слоя пока не распознаётся.

**Статус:** код стартового прототипа. Главный API-сценарий проверен автоматическим тестом и пройден в локальном браузере; публичный деплой, пилот с реальными пользователями, метрики качества ранжирования и реальная интеграция ФСП не выполнены. Подробное покрытие — в [статусе реализации](docs/implementation-status.md).

В `main` интегрирован [Signal v2](docs/superpowers/specs/2026-10-05-signal-v2-design.md): версионированные карточки ролей, предпочтения и приватность кандидата, evidence, версия подбора `match_v2`, закрепление условий в приглашении и лента актуальных ролей с сохранением/скрытием. Кандидат не отправляет отклик из ленты: основной контакт остаётся за работодателем. Фактическое покрытие и следующий этап — в [handoff](docs/next-agent.md); основания продуктовых решений — в [ресерче](docs/research/PRODUCT_RESEARCH.md).

Также перенесена ветка `codex/signal-product-polish`. Добавлены календарь HR со слотами 20/30 минут и бронированием по ссылке, заметки/аудио/расшифровка встречи с согласиями, Qwen-итоги и карточки со свайпом/объяснимым процентом совпадения. Полный pipeline и задачи следующего участника — в [новом handoff](docs/CALENDAR_MATCH_HANDOFF.md). Автоматический ASR требует отдельного speech-провайдера; chat API его не заменяет. При локальном падении Docker на `dockerInference` читать [инструкцию восстановления](docs/DOCKER_WINDOWS_RECOVERY.md).

## Быстрый запуск через Docker Compose

Нужен работающий Docker Engine. Эта сборка рассчитана на локальную демонстрацию с синтетическими данными; веб-адрес привязан к `127.0.0.1`.

```powershell
docker compose up --build -d
docker compose run --rm api python -m backend.seed_demo
docker compose ps
```

Откройте `http://127.0.0.1:8080`. Почтовый ящик Mailpit — `http://127.0.0.1:8025`. Swagger — `http://127.0.0.1:8080/api/docs`, OpenAPI — `/api/openapi.json`.
Если порт 8080 занят или зарезервирован системой, перед запуском задайте `$env:FSP_WEB_PORT='58080'` и открывайте сайт, Swagger и ссылки из писем на `http://127.0.0.1:58080`. Значение порта задавайте в том же терминале, где вызываете `docker compose`.

Демо-работодатель: `employer@demo.test` / `DemoPass123!`. Второй работодатель: `other@demo.test` / тот же пароль. Seed создаёт 96 **синтетических** кандидатов (по 12 на категорию); любой из них входит по адресу вида `backend-middle-1@demo.test` и паролю `DemoPass123!`. Для настоящего прохождения теста зарегистрируйте нового кандидата, откройте письмо подтверждения в Mailpit и войдите.

Последовательность показа: работодатель создаёт/выбирает потребность → открывает подборку → отправляет приглашение → кандидат принимает → тот же работодатель видит контакты, другой не видит.

На 7 октября полный локальный Compose-стенд проверен на Windows с портом 58080: PostgreSQL-миграция, API readiness, web, worker, Mailpit, регистрация, доставка письма, подтверждение email и вход. PDF-паспорт с кириллицей сформирован и прочитан в Linux-контейнере. Публичный HTTPS-стенд и внешний SMTP ещё не проверены.

## Локальный запуск без контейнеров

Используйте Python 3.12 и Node.js, совместимый с зафиксированным Vite. Команды ниже — PowerShell из корня проекта.

```powershell
python -m venv .venv
& '.venv/Scripts/python.exe' -m pip install -r backend/requirements.txt
$env:APP_MODE='demo'
$env:DATABASE_URL='sqlite:///./fsp_signal.db'
$env:PUBLIC_BASE_URL='http://127.0.0.1:5173'
& '.venv/Scripts/alembic.exe' upgrade head
& '.venv/Scripts/python.exe' -m backend.seed_demo
& '.venv/Scripts/python.exe' -m uvicorn backend.main:app --host 127.0.0.1 --port 8000
```

В другом терминале:

```powershell
cd frontend
npm ci
npm run dev
```

Откройте `http://127.0.0.1:5173`. Для регистрации нового аккаунта потребуется SMTP на `localhost:1025`: можно поднять сервис `mailpit` из Compose после запуска Docker и отдельно запустить worker:

```powershell
& '.venv/Scripts/python.exe' -m backend.mail_worker
```

Без SMTP можно войти в заранее подготовленные синтетические аккаунты; подтверждение нового email в браузере не сработает, пока письмо не доставлено. Автоматический API-тест проверяет сам механизм подтверждения.

## Проверки

```powershell
& '.venv/Scripts/python.exe' -m pytest -q
cd frontend
npm run build
npm run test:e2e
```

Для E2E нужен установленный Chrome и Python-окружение `.venv` в корне проекта (`Scripts/python.exe` на Windows, `bin/python` на Linux/macOS). Если окружение находится в другом месте, задайте `FSP_SIGNAL_E2E_PYTHON` как абсолютный путь к его интерпретатору. Playwright запускает API и Vite на случайных локальных портах в разных диапазонах, мигрирует временную SQLite и удаляет её после прогона.

Последняя итерация 7 октября: **140 backend passed / 9 PostgreSQL-only skipped**, **20 Playwright passed / 3 opt-in live-AI skipped**, TypeScript/Vite build и Compose config прошли; реальный Qwen summary проверен отдельно. Новая PostgreSQL-миграция/гонка бронирования ещё требуют проверки после восстановления Docker Desktop. Ранее, до добавления календаря, проходили 81 тест на PostgreSQL и полный Compose smoke; эти результаты не заменяют проверку новой миграции. Это ещё не измерение качества найма или сравнимости сложности теста на людях.

## Устройство

- `frontend/` — React, TypeScript, Vite; два кабинета.
- `backend/main.py` — HTTP API и серверные ограничения доступа.
- `backend/assessment.py` — четыре версии тестов с параметрами и фиксированной рубрикой; ключи ответов остаются на сервере.
- `backend/resume_import.py` — извлечение черновика профиля из текстового PDF без хранения файла.
- `backend/matching.py` — фильтры, прозрачная формула, объяснения.
- `backend/models.py`, `backend/migrations/` — SQLAlchemy и начальная Alembic-миграция.
- `backend/mail_worker.py` — SMTP-очередь на таблице БД.
- `backend/seed_demo.py` — синтетические данные, только для `APP_MODE=demo`.
- `infra/`, `compose.yaml` — контейнеры API, миграций, worker, PostgreSQL, Caddy и Mailpit.

На локальном dev используется SQLite; Compose использует PostgreSQL. Рекомендуемая конфигурация для публичного стенда потребует домен, HTTPS, действующие секреты, SMTP, отдельную политику хранения данных и проверку в реальной среде.

## Важные границы

API реестра ФСП организаторы не предоставили. Режим `mock` допустим только в демо; введённый произвольный ID помечается `unverified` и бонуса не даёт. Демо-кандидаты с баллами из seed помечены `synthetic_fixture`. Новый кандидат проходит реальный evaluator. Алгоритм тестов и поиск требуют отдельного экспертного и пользовательского пилота; численные цели в спецификации не являются достигнутыми результатами.
